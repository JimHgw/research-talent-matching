## 一、迭代目标与开发指导

本轮目标是让前后端更容易理解、独立测试和安全修改，同时保持现有 API 与业务语义兼容。先以“文档提取结果导入档案”为前后端协同分层试点，再整理档案确认、匹配、查询和用户反馈。

PDF 介绍的是 React/TypeScript 前端架构。采用其中的职责分离思路，按下列分工实施；PDF 中的目录、类名和示例代码是参考资料，不是用户要求机械照搬示例的实施指令。

### 前端职责

| 前端层次 | 开发责任 | 约束 |
|---|---|---|
| View / 页面 | 渲染表单、列表、弹窗和可访问的反馈，转交用户操作 | 多请求编排、草稿和版本状态变化交给专用 Hook 或 UseCase |
| ViewModel Hook | 管理交互状态、草稿、选中部分、确认勾选、请求生命周期和操作可用性 | 保留未保存/提交中保护和过期响应保护；不在 View 与 Hook 中重复维护同一状态 |
| UseCase | 表达加载审核、导入选定部分等有业务意义的操作 | 显式接收依赖，不依赖 JSX、React state 或翻译函数；普通函数足够时无需 class |
| Repository / 边界适配层 | 定义面向业务的数据操作，校验关键响应并执行必要转换 | 复用现有 API 客户端，避免只给每个客户端方法换名字的包装 |
| API Client | 处理 HTTP、会话、CSRF、JSON、上传、下载和传输失败 | 保留会话初始化与 CSRF 代次保护；按需通过业务方法贯通读请求取消 |

在应用或功能组装入口创建稳定的依赖，并传给 ViewModel/UseCase。保留现有功能边界，包括已有的文档审核复用档案字段组件的约定。围绕试点逐步引入类型，不将全应用迁移作为前置条件。

### 后端职责

| 后端层次 | 开发责任 | 约束 |
|---|---|---|
| HTTP 路由 | 读取参数、调用身份/CSRF 校验、校验请求 DTO、调用业务操作、输出响应 | 不编排档案更新、标签创建和来源更新等完整业务流程 |
| 应用服务 / UseCase | 表达一个业务操作，组织版本检查、状态变化及数据访问 | 不读取 Flask 的 `request`，不依赖页面状态；函数即可，不要求每项操作建 class |
| Repository | 查询、关联对象读写、批量加载和持久化 | 使用调用方提供的 Session，不自行提交事务 |
| DTO / 序列化 | 输出契约字段、处理时间格式和允许公开的字段 | 区分本人完整档案与研究团队可见档案 |
| ORM / 数据库 | 表结构、唯一约束、外键和持久化一致性 | 不把 ORM 对象直接当所有接口的返回结构 |

**事务约定：**业务操作定义哪些修改必须原子完成；HTTP、Worker 或 CLI 调用入口统一开启事务，鉴权、应用服务和 Repository 使用同一个 Session。Repository 不 `commit()`，服务不再嵌套开启另一笔写事务。文件解析和模型推理不进入写事务。现有数据库写锁在并发验收通过前保留。

**本轮范围：**沿用 React/Vite、Flask、SQLAlchemy、MySQL 和现有 `/api/v1` 路由，优先渐进整理内部实现。新增字段、错误码或请求语义必须同步契约、示例和前后端测试。前端范围包括有限的 TypeScript 试点、审核 ViewModel、查询/轮询状态、编辑一致性和匹配展示。后端继续负责最终权限、版本、事务完整性和评分。产品流程变更、新增公开端点或全应用重写需要另行明确范围。

### 全部任务必须保持的业务规则

1. 文档 `READY` 只表示提取完成。提取、导入档案、确认档案是三个不同动作；导入不能自动确认。
2. 每次成功导入均使档案 revision 加一，并清除 `confirmedRevision`、`confirmedAt`，状态变为 `UNCONFIRMED`。普通无变化保存保持 revision 和确认信息不变。
3. 团队发现与匹配要求当前档案已确认、确认版本等于当前版本、用户已授权发现；评分、排序、筛选和证据只能使用允许团队查看的字段。
4. 本人查看自己的匹配可以使用本人数据；团队接口必须采用团队可见数据投影。完整简历、原文件、文档来源和存储路径保持本人私有。
5. 部分导入未提交的部分保持原值及来源；允许清空的列表用 `[]` 清空，文本用 `""` 清空。共享标签解析造成的补充，沿用当前约定并返回规范化结果。
6. 实际修改的并发写入不能覆盖彼此；冲突返回 `409 / REVISION_CONFLICT` 和 `error.currentRevision`，失败操作不遗留部分写入。
7. 机会到达截止时间即过期；单纯修改截止时间不能自动重新开放，重新开放必须显式请求并通过权限、版本和发布条件校验。
8. 模型不可用时采用已有结构化回退。缺少证据不能编造成匹配成功，语义相似度不能替代明确缺口或硬性学历等条件。
9. 后台刷新不能默默替换未保存草稿。为旧文档、筛选条件、页码或账户发起的读请求，不能填入当前上下文。
10. 超时或被取消的写请求可能已经在服务端提交。不能将取消表述为回滚，也不能自动重放结果不确定的写入；应保留草稿并提供读取/对比恢复路径。
11. 浏览器展示服务端权威的确认、隐私和匹配结果，不自动确认导入后的档案、不另算推荐总分，也不代替后端执行最终权限校验。

## 三、前端开发与验收要求

### FE-1：建立类型化数据边界与前端回归基线

**难度：7/10。**需要同时处理 JS/TS 渐进共存、运行时契约校验和稳定依赖组装，并保留现有会话行为。

**目标：**为审核试点建立小范围、可验证的 TypeScript 基础，使前端对关键数据的假设与现有 API 契约一致。

**开发要求**

1. 核对现有 API 客户端、共享 Hook、文档审核和前端测试，记录提交号、环境、已执行检查和通过/失败/跳过数量。与 BE-1 对齐请求/响应及错误测试样例。
2. 增加 TypeScript 工具及使用 `tsc --noEmit` 的独立 `typecheck` 脚本。允许 JS/TS 共存，对新增类型模块启用严格检查，明确检查范围，避免无关的旧 JavaScript 迁移阻塞试点。
3. 定义改动流程所需的档案版本/确认、提取结果、审核部分输入、API 错误和匹配分数 DTO 类型。区分传输数据与可编辑的页面状态；结构确实相同时复用类型。
4. 引入文档/档案 Repository 边界和稳定的功能/应用依赖组装，复用 `createApi`、会话/CSRF 行为和现有业务方法。Repository 或 UseCase 应提供校验、转换、编排或有价值的依赖替换边界。
5. 在关键外部数据进入应用前执行运行时校验，包括审核提取结果、档案/版本响应、apply 结果和本轮改动的匹配分数结构。收到的 JSON 校验前视为不可信，类型断言不能替代校验；校验器与样例保持契约一致。

**验收要求**

- 新增 `typecheck` 脚本与 Vite 构建在 JS/TS 混合模块下通过。改动的类型边界不通过 `any`、宽泛断言或抑制检查指令绕过校验。
- 合法契约样例可正常加载；畸形版本号、确认结构、提取部分和分数数据进入可控的无效响应状态，不造成渲染崩溃或错误启用可写入操作。
- 无效的成功写响应按“结果不确定，需要核对”处理，不能据此断言服务端已回滚。
- 未改动调用者的 API 方法签名保持兼容。Cookie、CSRF 配对、上传/下载和进行中的会话初始化仍有回归覆盖。
- 测试可向业务操作传入内存/假 Repository，无需挂载应用或启动 Flask；生产依赖在重新渲染时保持稳定。
- 提交前端基线报告、契约与校验器/样例的对应表，以及与 BE-1 约定的接口预期；明确记录已有失败和跳过项。

**交付物：**限定范围的 TypeScript 配置与脚本、DTO 类型及 Repository 边界、关键响应校验器、依赖组装、边界测试和前端基线报告。

### FE-2：抽取文档审核 ViewModel 与 UseCase

**难度：7/10。**需要拆分有状态审核流程，同时保留草稿、版本、确认勾选和提交保护。

**目标：**将审核流程与渲染分离，保留现有文档身份、用户修正、确认勾选和导入保护。

**开发要求**

1. 从 `ExtractionReview.jsx` 抽取专用 `useExtractionReviewViewModel`，集中管理草稿、选中部分、确认勾选、加载/提交/错误/冲突状态、dirty 状态、关闭保护及派生的 `canApply`。
2. 抽取 `LoadExtractionReview`、`ApplyReviewedExtraction` 等有业务意义的普通操作。读取提取结果与当前档案，校验选中文档身份和 READY 状态，使用实际加载供本次审核的版本提交选定内容。
3. JSX、标签、翻译和布局留在 View，注入 FE-1 提供的 Repository/UseCase，复用现有 `useMutation`、导航保护、档案字段编辑器和恢复组件。
4. 与 FE-3 协调查询状态改动。后台结果不能默默替换审核草稿或更新其提交版本；切换文档或显式重新加载时，先经过现有放弃修改/提交中检查，再建立新的审核上下文。
5. 保留部分替换/清空语义和显式确认勾选。导入成功后进入更新后的未确认档案，不能自动调用确认接口。

**验收要求**

- View 不再直接编排并行 API 请求、版本选择或导入状态变化；加载/导入操作可通过注入依赖独立测试。
- 先加载文档 A 再切换 B，即使 A 最后返回，也不能在 B 的审核中显示 A 的建议；文档 ID 不匹配或结果非 READY 时不能启用导入。
- 修改值或选中部分会重置确认勾选。未选择部分、未确认理解影响、正在提交或冲突未解决时不能提交；快速重复点击只发出一个 apply 请求。
- 成功请求只提交选中部分和本次审核加载的版本。未提交内容由 API 保留；界面展示规范化保存结果，并保留独立确认步骤。
- 遇到 `409 / REVISION_CONFLICT` 时保留修正且不自动重试；提供读取/对比最新档案，或明确放弃后重新加载的恢复路径。
- 关闭、转手动录入和重新加载均保留现有 dirty/pending 保护。已卸载的审核不能在另一审核或账户中执行过期成功回调。
- 复用并通过相关 `task-61-document-review.test.js` 和文档提交测试；与 BE-2、BE-3、BE-4 完成真实 API 审核/导入/确认链路后方可验收。

**交付物：**审核 ViewModel、加载/导入 UseCase、简化后的 View、状态变化说明及独立操作/UI/联调回归证据。

### FE-3：改善查询刷新、读请求取消与文档轮询

**难度：8/10。**共享查询语义影响多个使用方，需要同时正确处理取消、竞态、轮询定时器和权限失效。

**目标：**在安全的后台刷新期间保留有用内容，明确读取和轮询生命周期，防止展示过期或无权访问的数据。

**开发要求**

2. 同一已授权资源上下文刷新时，保留上次成功数据并展示刷新状态；账户、选中实体、页码或筛选条件改变时清除旧上下文数据。失去权限时移除受保护内容，不能仅在旧数据上附加刷新错误提示。

5. 明确可见性/卸载规则：页面隐藏时不新发轮询；返回页面时，仅在仍有处理中工作且原预算未过期时继续检查。预算过期后保持暂停，直到显式刷新。保留手动录入和错误恢复。

**验收要求**

- 首次进入显示加载；同上下文后台刷新保留列表并显示刷新指示。可恢复的传输失败说明刷新未成功，同时保留最后已授权结果。

- 使用假计时器验证：最多同时有一个轮询请求，终态/卸载/隐藏时停止，按预算暂停并仅按约定恢复。重新挂载或 Effect 重跑不会产生重复定时器/监听器。
- 超出预算但仍为 PROCESSING 的文档显示等待/暂停，不能显示为 FAILED。手动刷新或新上传成功重新开始检查，手动档案录入始终可用。

**交付物：**一致的编辑 ViewModel/恢复行为、失效规则、延迟请求/会话测试，以及档案/隐私/机会真实 API 联调证据。

### BE-2：抽取文档审核导入应用服务

**难度：7/10。**需要抽取多步骤导入流程，并保持事务原子性、来源记录和版本语义。

**目标：**将文档导入流程从 HTTP 路由中抽出，并保持用户审核结果的原子写入。

**开发要求**

1. 从 `documents/routes.py` 抽取 `ApplyReviewedExtraction` 等业务操作，组织所有权、提取状态、档案版本、选中部分、标签解析、来源记录和确认失效。
2. 查询/写入放入文档或档案 Repository，序列化采用独立模块；移除 documents 对 profile 路由模块的导入。

- 业务操作可直接调用测试；原有 HTTP 与前端审核联调仍通过。

**交付物：**导入服务、必要的数据访问/序列化模块、直接调用测试及原有审核流程回归报告。

### BE-3：整理档案保存与确认服务

**难度：6/10。**围绕已有保存/确认规则整理共享查询和序列化，需要保留无变化保存及标签行为。

**目标：**集中管理档案状态变化，供文档导入和本人档案操作复用。

### BE-4：验证并发版本控制与事务原子性

**难度：8/10。**需要在 SQLite、MySQL 上控制多连接并发与故障注入，证明状态变化和回滚正确。

**目标：**证明真实并发时不会丢失更新，并为后续分层提供保护。

**开发要求**

1. 审核档案、隐私、导入和机会写操作：事务必须在读取用于版本比较的状态之前建立所需写保护。
2. 保留现有 MySQL 写锁和 SQLite 写事务保障。采用两个独立数据库连接/请求复测，不用单连接顺序调用代替并发验证。
3. 给档案子表、个人标签、来源、确认状态等写入设置故障注入，验证同事务回滚。
4. 区分重复确认、普通无变化保存和重复导入；保持现有版本协议，不因重试默默重复执行导入。

**验收要求**

- 两个携带同一 revision、都会真实修改档案的请求并发执行，恰好一个成功，另一个 `409`；最终数据库只包含成功请求的完整结果。
- 导入与手动保存竞争同一版本时满足同一规则；成功导入只产生一次版本递增。
- 确认与编辑并发的结果必须对应合法串行顺序：新内容不能携带旧版本确认。编辑先完成时旧版本确认应返回 `409`。
- 使用同一旧版本重试已成功导入的请求返回 `409`，不再次创建标签或递增版本。
- 任一子表写入中途失败，revision、确认、标签、内容及来源一起回滚。
- 关键用例在 SQLite 和真实 MySQL 8.4 均执行；提交两类结果。用例至少重复运行 10 轮且不依赖睡眠碰运气，可使用同步屏障控制交错顺序。

**交付物：**并发/故障注入用例、事务边界说明、双数据库测试结果。锁粒度优化如确有必要，应另附测量与正确性对照。

### BE-5：统一授权与团队可见数据边界

**开发要求**

1. 复用现有会话、角色、CSRF 校验，列出本人、其他人才、机会所有者、其他团队、匿名和失效会话的权限矩阵。
2. 整理“当前已确认 + 已授权发现 + 用户有效 + 字段可见”的团队查询入口，覆盖列表、详情、匹配和收藏/shortlist 相关路径。
3. 在进入搜索和评分前构造团队可见数据；禁止先对隐藏内容评分再只删除输出字段。
4. 审核 `resumeDescription`、原文档、提取结果、origins、个人标签和语义输入；本人数据与团队投影保持明确边界。

**验收要求**

- 匿名访问私有接口 `401`，错误角色 `403`；未获授权的私有资源按既有契约 `404`，不泄露其存在性。
- 修改两个均符合发现条件的测试档案中的隐藏内容、并分别重新确认后，团队端筛选命中、评分、排名和证据不受隐藏内容影响。
- 撤回发现授权或隐藏字段后，下一次新请求立即遵守新权限；既有收藏不能绕过检查。
- 修改档案但尚未重新确认时，团队不能继续使用旧确认内容；本人推荐/匹配按契约拒绝未确认档案。
- 团队响应及模型输入不包含完整简历、原文档路径/ID 或私有来源；其他账户无法读取本人文档或使用其个人标签。
- 登出、会话过期和账户切换用独立客户端验证，不能依靠前端隐藏按钮通过验收。

**交付物：**权限矩阵、统一数据边界的必要整理、API/评分输入断言和回归报告。

### BE-6：验证 Worker 恢复与状态一致性

**难度：8/10。**需要可复现的多进程租约恢复、重启验证，以及对过期 Worker 迟到写入的拒收。

**目标：**确认已有租约机制在重启、多进程和超时场景下仍可靠。

**开发要求**

1. 保留 `QUEUED → PROCESSING → READY/FAILED`、租约 token、过期重领和最大尝试次数规则。
2. 梳理领取任务、解析文件、校验结果、写回状态的边界；文件解析在写事务外进行。
3. 对照现有 `test_us09_worker.py`，补齐尚缺的跨进程停止/重启验证；已覆盖的场景直接复用。
4. 区分租约过期、文件损坏、模型/解析异常和结果 schema 错误，记录可定位的处理阶段与结果。

**验收要求**

- 两个独立 Worker 同时运行时，同一文档的同一租约只能被一个领取。
- Worker 在 PROCESSING 后被停止，租约到期后另一个 Worker 能接手；成功后状态为 READY 且只有一份有效提取结果。
- 旧租约持有者延迟返回成功或失败，均不能覆盖新租约或 READY 结果。
- 达到最大尝试次数后文档为 FAILED；文件缺失/损坏进入可识别失败，用户仍能手动维护档案。
- 提取结果 `documentId` 不匹配或 schema 无效时不能写入 READY；后续可按租约恢复规则处理。
- 上传文件已保存但数据库登记失败时，文件按已有补偿逻辑清理；失败日志不输出简历正文。

**交付物：**Worker 行为说明、可复现的恢复步骤、回归用例与至少一份进程重启实测记录。

### BE-7：固定逐条需求评分与模型回退行为

**难度：9/10。**同时涉及逐条需求评分正确性、硬性证据约束、真实模型资源和故障/冷却恢复。

**目标：**让现有 MiniLM 逐条需求评分可解释、可复现，并在模型不可用时保持 API 可用。

**开发要求**

1. 整理现有 `requirement_scoring.py`、`semantic_runtime.py` 的调用边界，明确结构化判定、语义评分、总分和解释的职责。
2. 保持 REQUIRED=2、PREFERRED=1 的权重；总推荐分按现有逐条需求规则计算，不能再叠加整体兴趣相似度作为额外奖励。
3. 保留请求内文本去重、批处理、校验过的本地模型、失败冷却和结构化回退。记录模型、预处理/评分算法及阈值版本。
4. 增加必跑的真实应用模型检查：准备 `data/semantic/model` 所需资源；历史 US-13 实验的模型/报告不能替代当前逐条评分验证。
5. 真实模型验收入口在资源缺失时必须明确失败，不能因现有 `skipif` 自动跳过后仍宣告语义功能通过。

**验收要求**

- 所有已支持的需求类型均有逐条评分；权重、分母、舍入及总分与独立计算的固定样例一致。
- 缺少证据、明确缺口、学历层级/成果类型不符合时，不能被较高相似度升级为已满足；兴趣文本不能充当技能或学历证据。
- 同一数据的列表、详情、收藏相关匹配结果采用相同规则；排序使用全体合格候选的最终分数。
- 模型文件缺失/损坏、加载失败、推理抛错和无效向量时，接口返回契约允许的结构化回退及不可用标识，不产生 NaN 或伪造语义证据。
- 故障冷却期不会每个请求重复加载；冷却结束可恢复。请求处理期间不下载模型。
- 至少有中文同义表达、含义不同和明确否定的真实模型 HTTP 用例执行成功；提交模型版本及无关键跳过的报告。
- 沿用当前不跨请求保存档案文本/向量的边界；若未来增加缓存，另行设计授权及版本失效规则。

**交付物：**评分规则说明、固定样例、故障回退测试、真实模型执行报告及模型准备/校验步骤。

### BE-8：优化查询、过滤与分页

**难度：9/10。**需要优化数据加载和 SQL，同时保持全局语义排序、准确筛选、总数及稳定分页不变。

**目标：**降低不必要的数据加载和关联查询，同时保持查询结果与推荐语义一致。

**开发要求**

1. 先测量机会列表、本人推荐、团队人才匹配的 SQL 数量、候选数、P50/P95 和峰值内存，再选择优化点。
2. 对普通机会列表，将适合数据库执行的授权、有效期、组合过滤、稳定排序、count 和分页下推；无法直接下推的规则单独说明等价实现。
3. 对关联标签和结构化记录采用批量读取，避免每个候选追加相同查询；索引依据实际查询和执行计划增加。
4. 对推荐保持“权限过滤 → 条件过滤 → 对全部合格候选评分 → 稳定排序 → 分页”。不能先取一页或任意截断候选后再评分。
5. 统一机会有效期规则及单次操作使用的时间，保留显式 reopen 和旧客户端省略可选字段时的兼容行为。

**验收要求**

- 同一数据、固定时间和模型下，优化前后结果集合、顺序、total 和 rank 完全一致；分数仅允许现有舍入精度内差异。
- 截止时间前、等于截止时间、截止时间后均符合既有规则；编辑未来截止时间不会使已过期机会自动开放。
- 采用同一固定数据集：100 和 1,000 个候选，各含混合权限、状态和过滤条件；每组预热后至少采集 30 次请求，提交同环境前后指标。
- 普通机会列表不再先序列化所有候选再截取一页；关联读取 SQL 数量不随返回记录数逐条增长，报告实际查询上限。
- 多页查询无重复/遗漏，等分时稳定排序；仅筛选或分页不触发写入。
- 如果测量表明某项优化无收益或会改变排序，保留正确实现并提交测量结论；不能以改变业务结果换取性能数据。

**交付物：**查询整理、必要索引、结果等价性测试、固定数据和前后性能报告。

### BE-9：统一数据库升级与发布前检查

### BE-10：完成联调、诊断和交付验收

**难度：7/10。**需要整合 CI、诊断和真实 API/Worker/模型链路，协作与验收取证工作较多。

**目标：**让团队能够证明本轮改进有效，并定位用户遇到的真实失败。

**开发要求**

1. 复用现有 CI 的后端、MySQL、前后端联调和语义评估作业，纳入本轮新增用例及 BE-7 的真实应用模型必跑检查。
2. 统一保存测试数量、失败/跳过、模型版本、提交号和环境信息；当前逐条需求评分不能只引用历史实验报告验收。
3. 沿用现有 `requestId`、`X-Request-Id`、`/healthz`。补足需要的阶段、耗时、错误类型、版本冲突和模型回退诊断；Worker 使用不含正文的任务关联标识。
4. 与前端/QA 联调完整流程和失败恢复，提交可重放的数据、操作及预期；修复项应对应复现步骤和复测记录。纳入 FE-5 的前端报告，将各场景关联到对应 FE、BE 负责人。
5. 日志不得包含密码、Cookie、CSRF token、完整档案/简历、模型输入或私有存储路径。

**验收要求**

- 现有相关回归和本轮新增检查全部通过；MySQL、真实应用模型及必须的前后端联调用例不能被跳过后当作完成。
- 至少实测以下链路：上传 → Worker 提取 → 用户选择部分导入 → 档案未确认 → 显式确认 → 匹配；另测审核期间其他请求修改档案、旧版本导入冲突、隐私撤回、模型故障回退及机会过期/reopen。
- 冲突不会覆盖数据库中较新内容；前端保留草稿的责任由前端联调验证，后端不得靠自动重试旧写入规避冲突。
- 注入一次请求失败，可按响应 requestId 找到对应诊断；可按任务关联标识追踪 Worker 领取、重领和结果写回。诊断数据经检查无敏感正文。
- API/Worker 重启后已保存数据仍可读取；数据库不可用时就绪检查失败，模型不可用但结构化回退仍可用时按回退状态报告，不误报整体停服。
- 发布说明覆盖接口影响、数据库升级、模型资源、已知限制和恢复步骤；每个任务都有 MR/提交及验收证据对应。

**交付物：**CI 更新、联调与故障恢复报告、必要诊断改进和统一发布说明。

## 六、统一完成标准与验收记录

任务完成需要同时满足：实现可审查、业务行为符合要求、契约同步、测试实际执行、失败恢复可复现。仅提交目录调整、测试文件或“手动看起来正常”不足以验收。

前端检查包括现有测试、构建、格式脚本，以及 FE-1 新增、FE-5 设为必跑的 `typecheck` 脚本。typecheck 是 Sprint 3 交付要求，不表示基线中已经存在。API mock 适合独立 UI/竞态测试；最终跨层验收须执行相应真实后端、数据库、Worker 和模型检查。

每个任务提交一条下列记录：

| 记录项 | 必填内容 |
|---|---|
| 任务与实现 | FE-x 或 BE-x 编号、实际负责人、MR/提交 |
| 环境 | 数据库版本、Python 版本；涉及模型时记录模型/算法版本 |
| 执行情况 | 命令或操作步骤、数据版本、执行时间、通过/失败/跳过数量 |
| 结果证据 | 响应、数据库断言、报告或日志关联标识；不得保存敏感原文 |
| 风险与恢复 | 已知限制、契约/升级影响、恢复方式 |
| 验收结论 | 通过 / 不通过；未完成条件明确列出 |

仓库已有 `--run-mysql` 与 `--require-frontend` 测试选项，应复用。MySQL 测试会清理测试数据，必须使用名称以 `_test` 结尾的专用隔离数据库，按 `backend/tests/conftest.py` 和现有 CI 配置运行。

前端记录还须按适用范围包含 Node.js、包管理器和浏览器版本，以及可用性证据对应的视口/语言设置。分别记录前端测试、构建、格式和 typecheck 的提交号及结果。
